# Research Assistant

Evidence-grounded research over trusted sources. The system answers **only** from
retrieved documents, verifies every citation against its own stored copy of the
source, and **refuses to answer** when the evidence does not support one.

> ### Evidence > fluency
> A short answer with strong evidence beats a detailed answer containing
> unsupported information. When the evidence is weak, the system says so.

---

## Why this is different from a normal RAG app

Most RAG systems ask the model to write citation markers into its prose. A model
can fabricate `[1]` as easily as it can fabricate a fact.

This system does three things instead:

| | Mechanism | Enforced by |
|---|---|---|
| **1** | Citations are generated by the **Claude Citations API** against the actual document content, not written by the model into prose | The API |
| **2** | Every returned citation is re-checked against our **own stored chunk text**; anything that doesn't match verbatim is dropped | Code (`citations/validator.py`) |
| **3** | The answer is decomposed into claims, each checked against retrieved evidence; if too few survive, the answer is **withheld entirely** | Code (`citations/verifier.py`) |

Steps 2 and 3 hold **regardless of model behaviour**. They are `if` statements,
not instructions.

## The pipeline

```
question
   │
   ├─ validate input ......................... reject empty / oversized / control chars
   ├─ decompose (research mode) .............. subquestions
   ├─ hybrid retrieval ....................... dense + BM25, fused by RRF
   ├─ tier filter + rerank + diversify ....... official sources preferred
   │
   ├─ GATE 1: enough evidence? ............... else REFUSE (no model call made)
   │
   ├─ generate with Citations API ............ documents attached, citations enabled
   │
   ├─ GATE 2: model declared insufficient? ... else REFUSE
   ├─ validate every citation ................ unverifiable ones dropped
   ├─ verify every claim ..................... supported / unsupported / contradicted
   ├─ GATE 3: enough claims supported? ....... else REFUSE
   │
   └─ answer + citations + evidence + caveats
```

**Every gate can only reduce confidence.** There is no path that adds an
unsupported claim back in.

Full detail, including the two-call constraint: **[ARCHITECTURE.md](ARCHITECTURE.md)**

## Source trust model

Trust is decided **at ingestion, from the URL** — never from document content.
A document instructing the system to trust it has no route to do so.

| Tier | What | Examples |
|---|---|---|
| **1** | Official docs, government, standards bodies, peer-reviewed | `docs.anthropic.com`, `docs.aws.amazon.com`, `kubernetes.io`, `*.gov`, `*.gc.ca`, `nature.com`, `ietf.org` |
| **2** | Universities, research institutions, recognised technical orgs | `*.edu`, `arxiv.org`, `apache.org` |
| **3** | Reputable secondary | `wikipedia.org` |
| **4** | Everything else — **never authoritative alone** | blogs, forums, social media |

Anything unrecognised defaults to **Tier 4**, never Tier 1. Subdomains inherit,
but lookalikes do not: `docs.aws.amazon.com.evil.example` is Tier 4.

Configure via `RA_TRUSTED_DOMAINS_FILE` (JSON) or `RA_TIER1_DOMAINS` (CSV).

## Chunking

Two rules, both tested as invariants:

1. **No content loss.** Every block of a source document appears in at least one
   chunk, at every chunk size.
2. **Context is preserved.** Heading hierarchy travels with each chunk as a
   `section_path`, and overlap never crosses a section boundary — carrying one
   section's tail into the next would mislabel it.

Defaults: 400 tokens, 60-token overlap, split on sentence boundaries.

## Retrieval

**Hybrid, because real questions come in two shapes.** Dense vector search finds
paraphrase; BM25 finds exact strings — error codes, identifiers, proper nouns —
that embeddings handle badly. A user searching for `E4021` gets nothing useful
from semantic similarity alone.

The two ranked lists are fused with **Reciprocal Rank Fusion** rather than score
addition, because scores from two different systems aren't on a comparable
scale. RRF uses rank position only, which is what makes combining them safe.

Then: authority-aware reranking (relevance dominates, trust breaks ties) and
per-document caps so one long page cannot fill the whole context window.

⚠️ **Gating uses absolute relevance, never the ranking score.** The top hit for
*any* query normalises to ~1.0, so a ranking score cannot distinguish "best
match" from "good match". Refusal decisions rest on dense cosine similarity,
which is comparable across queries.

## Anti-hallucination measures

| Requirement | How it's enforced |
|---|---|
| Never invent facts | Grounding prompt + claim verification + withholding |
| Never invent URLs | URLs come from stored metadata; the model never supplies one |
| Never invent citations | API-generated, then re-verified verbatim against stored chunks |
| Never fill gaps with model knowledge | Explicit prompt rule + claim verification against evidence only |
| Distinguish fact from inference | Prompt requires labelling; caveats surfaced in the response |
| Say when evidence is insufficient | Three independent gates, any of which triggers refusal |

**What a fabricated citation hits, in order:** the API won't produce it → the
validator rejects it (text not in the stored chunk) → the claim verifier marks
the claim unsupported → the claim gate withholds the answer.

## Evaluation

24 cases across five categories. **Half expect refusal** — a RAG system is easy
to score well on questions its corpus answers; what distinguishes a trustworthy
one is what it does with the rest.

```bash
python scripts/evaluate.py --dry-run          # $0
python scripts/evaluate.py --category hallucination_bait
python scripts/evaluate.py --save             # ⚠️ real API calls, costs money
```

Metrics: outcome accuracy · refusal accuracy · **false answer rate** · citation
correctness · citation completeness · groundedness · unsupported claim rate.

### Dry-run baseline

With the extractive stand-in model (`evaluation/fake_model.py`):

| Metric | Result |
|---|---|
| Outcome accuracy | 91.7% |
| Citation correctness | **100%** |
| Citation completeness | **100%** |
| Groundedness | **100%** |
| Unsupported claim rate | **0%** |
| False answer rate | 16.7% |

⚠️ **Read the failures honestly.** Four cases fail in dry-run, and **two of them
are limitations of the stand-in model, not the pipeline:**

- **M1, M2 (multi-source)** — the extractive fake quotes a single sentence, so it
  cannot synthesise across two documents. A real model can.
- **H1, H3 (false premise)** — detecting *"why does time slicing provide better
  isolation than MIG?"* as a false premise requires reasoning the extractive
  reader cannot do. The pipeline's defence against this is **contradiction
  detection in claim verification**, which the fake's naive verifier doesn't
  exercise.

These numbers are a **floor**, not a ceiling — they show what the pipeline
guarantees even with a model that cannot reason. Run without `--dry-run` for the
real figures.

```bash

```

| File | What it proves |
|---|---|
| `test_chunking.py` | No content loss at any chunk size; sections don't bleed; IDs stable |

| `test_citations.py` | **Fabricated quotes, wrong-document attribution, out-of-range indices all rejected** |

Tests script the model into misbehaving and assert the system catches it. None
rely on the model being well-behaved.

## Configuration

Every threshold is env-overridable — see [`.env.example`](.env.example). The ones
that change behaviour most:

| Variable | Default | Effect |
|---|---|---|
| `RA_MIN_SUPPORTED_RATIO` | `0.8` | Fraction of claims needing evidence before an answer is released |
| `RA_MIN_EVIDENCE_SCORE` | `0.30` | Absolute relevance required before the model is called at all |
| `RA_TOP_K` | `8` | Chunks passed to the model |
| `RA_MAX_PER_DOC` | `3` | Stops one document monopolising the context |
| `RA_WEB_RESEARCH` | `false` | Web research, allowlist-gated |

**Raise the first two to make the assistant more reluctant to answer.**

## Web research

Off by default. When enabled, it uses Anthropic's **server-side** `web_search` /
`web_fetch` with `allowed_domains` set to the trusted list.

⚠️ **This is the security design, not a convenience.** We never issue outbound
HTTP to a model-chosen URL, so there is **no SSRF surface**. The allowlist is
enforced server-side, where no prompt can talk its way around it. A test asserts
that no HTTP client is ever imported into `web_research.py`.

---

## Security

- Secrets from environment only; **nothing hard-coded** (asserted by a test that
  greps the source)
- A redacting filter on the root logger masks API keys, bearer tokens and DSN
  passwords — including inside exception text
- Input validation rejects rather than truncates; control characters stripped
- Per-client rate limiting
- Unhandled errors return a generic message; detail goes to logs only

## Known limitations

Stated plainly, because a system about honest evidence should be honest about itself:

- **Token counts during chunking are approximate** (~3.5 chars/token). Boundaries
  don't need exactness; the context budget check does, and that uses the API's
  own counter when credentials are available.
- **Conflict detection is prompt-driven.** The `SourceConflict` schema and the
  prompt rule exist, but conflicts are surfaced by the model rather than detected
  independently in code. Code-level contradiction detection across sources is the
  clearest next improvement.
- **Claim verification costs an extra call per claim.** Accuracy was prioritised
  over latency; batching is the obvious optimisation.
- **The in-memory store is not persistent.** Use `RA_STORE=pgvector` for anything
  real.
- **`HashEmbedder` is lexical, not semantic.** It exists to make tests
  deterministic and free. Never use it in production.
